# 需求规格与文档管理规范

## 分类和唯一来源

完整方案见[文档导航](../README.md)。目录职责固定：

- `requirements/`：当前业务需求规格，每个独立需求一个 REQ。
- `design/`：当前页面组织、交互流程和实际截图，引用 REQ，不重复定义业务规则。
- `changes/`：每轮实质澄清或页面变更的决策与差异，不能作为需求入口。
- `guides/`：流程、模板和调测方法；纯流程调整只更新这里和 AGENTS.md。
- `reference/`：用户提供的外部输入和原始版本，不自动等同当前规格。

澄清后的规则必须回写对应 REQ，不能只写在变更记录或设计图解中。规格、交互设计和当轮记录相互链接。

## 编号和版本

REQ 从现有索引递增，不复用编号；同一需求经过多轮讨论时更新已有 REQ，不按聊天轮数复制规格。新需求才创建新 REQ。

每轮实质业务澄清使用一份 `changes/CL-NNN-主题.md`，CL 为历史沿用编号；索引倒序，已删除或合并的编号不复用。采用[变更记录模板](change-record-template.md)。流程约定本身不额外生成无业务内容的记录。

REQ 与设计文档维护版本、更新日期及变更表。状态为草稿、待评审、已确认或已废弃；不因存在 demo 而声明评审通过。正式规格不含待确认事项，未明确规则应先使用提问工具讨论。

## 规格必备内容

使用[需求模板](requirement-template.md)，包含：背景和目标、角色及前提、范围、场景、业务规则、数据和明确的接口约定、异常与边界、可观察的验收标准、关联设计和变更历史。区分离线演示范围与真实服务集成，不将未知能力写成事实。

## 页面设计与截图

设计文档按功能组织交互与截图，并在开头显著说明本轮变化。截图保存在 `assets/screenshots/CL-NNN/`，以相对 Markdown 图片链接嵌入设计或变更记录，注明部门、视口、状态和体验路径。截图与文本共同描述关键流程，不能仅截首页。

旧布局截图只在历史变化中使用。现行设计引用当前有效截图；无前态不伪造，无业务页面变化不制造重复截图。没有实际截图时说明验证限制，不用原始设计图代替。

## 完成门槛

1. 通过提问明确规则，更新对应 REQ、设计及 demo。
2. 通过本地 HTTP 实际调测；发现布局或交互问题立即修复复测。
3. 刷新关键截图，记录本轮变化，维护各分类索引和链接。
4. 检查实际行为、文档和图片一致性，校验语法及链接。
5. 自动 commit、推送并核对远端，报告提交及验证范围。

删除重复文档前先合并有效信息、修正引用，并记录去向；历史通过 Git 保留，不另建重复归档副本。
