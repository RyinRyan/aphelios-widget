# 需求规格编写与管理规范

## 目的与范围

每个独立业务需求建立一份规格，描述用户目标、规则、交互、异常与验收。一个需求覆盖一组紧密关联的能力；不同业务目标或可独立验收的变化应拆分，并通过关联需求说明依赖。规格描述预期行为，演示实现和参考文档仅作为证据，不自动替代规格。

## 编号与目录

- 目录：`docs/requirements/`；文件名 `REQ-NNN-简短英文标识.md`，例如 `REQ-001-todo-widget.md`。
- 编号从 001 开始递增，创建前查看索引，编号一旦使用不复用；标题使用中文。
- 每份规格复制 [模板](requirement-template.md)，并在 [需求索引](../requirements/README.md)登记编号、标题、状态及关联演示。
- 图片或其他参考材料放在 `assets/design/`，规格中用相对路径链接，说明是原始参考还是当前设计；引用外部接口时写明来源和版本。

## 必备内容

1. **元信息**：编号、标题、状态、版本、创建和更新日期、负责人（未确定写“待定”）、关联资料。
2. **背景与目标**：问题、用户价值、目标及衡量方式；避免把具体页面实现当作业务目标。
3. **范围与非范围**：当前交付边界、外部系统职责与明确排除项。
4. **角色与前提**：用户、权限、触发条件及依赖。
5. **场景与交互**：入口、主要流程、界面元素、关键状态、批量及响应式/键盘行为；需要时附图。
6. **业务规则与数据**：来源、字段、筛选、规则、校验、状态及状态转换；列出接口契约或待确认项，不猜测外部能力。
7. **异常与边界**：空数据、失败、未配置、权限不足、重复操作、并发或混合选择等适用情况。
8. **验收标准**：使用可观察、可验证的条件；覆盖主流程、边界与异常，区分 demo 验收和实际集成验收。
9. **待确认事项与决策记录**：明确问题、影响及状态；不要把假设写成已确认事实。
10. **变更记录**：日期、版本和变更内容；Git 提交提供详细历史。

## 状态与维护流程

- **草稿**：仍在收集或设计；待确认事项显式列出。
- **待评审**：范围和验收条件足够评审，待相关方确认。
- **已确认**：相关方确认范围、规则及验收条件；后续变更更新版本和记录。
- **已废弃**：不再适用，记录原因和替代需求；保留文件与编号。

每次新增需求先创建规格并登记索引；交互或业务规则变化时，同步更新对应规格、演示和验收条件。提交前检查规格与实际演示是否一致，无法实现的部分明确标注。跨需求变更应更新所有受影响文档。状态调整应依据实际评审结果，不能因为 demo 存在就标记已确认。

规格版本可采用 `0.x` 表示草稿、`1.0` 表示首次确认，确认后小范围调整递增次版本；涉及范围或规则的重大变化递增主版本。版本仅用于规格，不替代 Git 版本。

## 完成检查

- 目标、范围、关键交互与业务规则可理解，未确定内容有记录。
- 验收标准可执行，演示行为与真实集成要求分别标明。
- 需求索引、相关文档和相对链接已更新；设计材料无敏感信息后再提交。
- 涉及页面变更时，检查离线打开、相关交互与适用的屏幕尺寸；无法执行的验证如实记录。
